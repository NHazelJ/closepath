  What exists

  The repo is still the scaffold plus docs:

  - Code: src/app/ contains only the starter page.tsx, layout.tsx and
    globals.css. There is no src/lib/ or src/server/ yet, and no components/ui
    (shadcn hasn't been set up).
  - Config: next.config.ts turns on cacheComponents and partialPrefetching.
    tsconfig.json is strict, with the @/* alias.
  - Placeholder folders: prisma/, e2e/, .github/workflows/ and .claude/agents/
    hold only .gitkeep. There's no schema, no listings.json and no CI.
  - Dependencies: only next, react, react-dom, Tailwind, ESLint and TypeScript.
    There's no Zod, Vitest, Prisma or faker.
  - node_modules is not installed. lint, typecheck and build can't run until npm
    ci does.
  - Rubric: docs/rubric-checklist.md already lists F1 listing search as the HW4
    Part 2 feature (Explore, then Plan, then Implement, then Commit), so this
    choice matches the plan.

  Is it reasonable and dependency-light?

  Yes, for the search logic. The full /listings page needs more.

  The search core fits in one pure module, for example
  src/lib/domain/listing-search.ts. It would take a list of listings, the raw
  searchParams and the page number, and return the matching page, the total
  count and any warnings. That one module covers:

  - F1-AC2: combined filters (city, min/max price, min beds, min baths, property
    type), parsed from the URL.
  - F1-AC3: sorting by newest, price low to high, or price high to low.
  - F1-AC1: 20 per page, with pagination math.
  - F1-AC4: an "empty" result the page can use to show "Clear filters".
  - F1-AC5: invalid values are ignored with a message (negatives, text in number
    fields, min price above max price).

  It follows ADR-5 (pure function, no database, no clock) and needs no runtime
  dependencies. Plain TypeScript narrowing is enough for parsing; Zod is
  optional.

  What it still needs:

  1. A test runner. Vitest is the one real dependency. CLAUDE.md says to ask
     before adding one, so I'll ask when we plan.
  2. Data. Without Prisma, the page would need a committed
     prisma/seed/listings.json (ADR-8 plans one anyway) or test fixtures.
     Filtering about 80 listings in memory easily meets the under-1-second
     target. When Prisma arrives, the same parsed filter can feed a Prisma
     query.
  3. Out of scope for this module: F1-AC6 to AC10 (listing detail page, saved
     homes, Request info, duplicate leads). Those need auth, a database and
     Server Actions.
  4. UI: a basic /listings page could use plain Tailwind for now. shadcn/ui can
     come later.

  in this session. If the log has to show those tools by name, the explore step
  may need redoing in a session that has them.

  Next step: Plan mode for the module's interface, with Vitest as the only
  dependency (after you approve it) and fixtures or a small listings.json for
  data.

     2. src/lib/domain/listing-search.ts: pure, no Zod, no clock. Property types
        are not hardcoded. They belong to the data (the future Prisma schema),
        so the module takes them as input. Named exports:
        - type PropertyType = string. The module never lists the values; tests
          use fixture values.
        - SORT_OPTIONS = ["newest", "price_asc", "price_desc"] as const. Sort is
          a UI concern, not data, so a constant is fine here.
        - PAGE_SIZE = 20
        - type ListingSummary: id, address, city, price (int), beds, baths,
          sqft, propertyType, status (ACTIVE | PENDING | SOLD), photoUrl,
          listedAt (Date). Only the fields the card needs.
        - type ListingFilters: all optional (city, minPrice, maxPrice, minBeds,
          minBaths, propertyType)
        - type ListingQuery: { filters, sort, page }
        - searchListings(listings, query) returns { items, total, page, 
          pageCount, pageSize, isEmpty }:
          - keeps only ACTIVE listings and applies every filter (AND); city
            matching is trimmed and case-insensitive
          - sorts, with ties broken by id so results are deterministic
          - clamps page to 1..max(pageCount, 1), then slices out 20
     3. src/lib/validation/listing-search.ts: Zod. Named exports:
        - listingSearchParamsSchema defines the per-field schemas:
          - prices are non-negative integers
          - minBeds is a non-negative integer
          - minBaths is a non-negative number, so 1.5 works
          - city is trimmed and non-empty
          - propertyType is validated against a list passed in by the caller:
            buildListingSearchParamsSchema({ propertyTypes }) uses
            z.string().refine(v => propertyTypes.includes(v)). Today the caller
            is the page with seed data; later it's the DAL, reading the Prisma
            enum or a lookup table.
          - sort is z.enum(SORT_OPTIONS)
          - page is an integer of 1 or more
          - numbers are coerced from strings with
            z.string().trim().pipe(z.coerce.number()...), so "" is treated as
            unset instead of 0
        - parseListingSearchParams(raw: Record<string, string | string[] | 
          undefined>, options: { propertyTypes: readonly string[] }) returns { 
          query: ListingQuery, warnings: string[] }:
          - takes the first value of array params
          - runs safeParse per field, so one bad value is dropped with a warning
            while the valid ones are kept (F1-AC5: "ignored, and a short
            message explains why")
          - cross-field check: if minPrice > maxPrice, both are dropped with the
            warning "Min price is above max price, so the price filter was
            ignored."
          - a bad sort falls back to newest, and a bad page falls back to 1,
            each with a warning
          - it never throws
     4. Test files next to the source: src/lib/domain/listing-search.test.ts and
        src/lib/validation/listing-search.test.ts. Each test name starts with
        its AC ID. Fixtures come from a small makeListing(overrides) factory

     Property-type source of truth (decided later, with the schema)

     Adding a type such as "Trailer" or "Land" must not require editing search
     code. With injection, the search and validation modules never change; only
     the source does. When Prisma is added (schema changes need approval),
     choose between:
     - a Prisma enum PropertyType: the DAL passes Object.values(PropertyType),
       and adding a type is a migration;
     - a PropertyType lookup table: the DAL passes the rows, and adding a type
       is a data insert with no migration.

     Until then, the seed or fixture data defines the list. A test asserts that
     an unknown type supplied by the caller is accepted, which proves the list
     isn't baked in.

  2. The code never sorts the input. listings.filter(...) always returns a new
     array, and .sort() runs on that copy.
